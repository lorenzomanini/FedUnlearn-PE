# Audit of the previous runtime changes

Scope: read-only comparison of `939ab74` (17 September) to `a95658c` (21 September), with earlier history (`29a7ebe`, `645bb69`, `d9dbd74`) checked for attribution. The uncommitted changes already present in README, analysis and queue files were not treated as algorithm changes. The prior Codex task “Fix unlearning runtime and LiRA” confirms that its changes correspond to this interval. “Diagnose algorithm time limit” diagnosed a GPU binary incompatibility, not an algorithm change.

## What the supplied CIFAR artifacts actually ran

`stat_tests/CIFAR/init_params.pkl`, `test_params.pkl`, logs and all three `score_diagnostics.pkl` agree: CIFAR10 random split; ResNet18, 11,181,642 scalar parameters; SGD learning rate 0.01, momentum 0.9; 40 original and gold epochs; one recovery epoch per case; ten score-mass fractions from 0 to 100%; three repetitions; eight LiRA shadows; LiRA cases 0, 5, 9 only. Full autograd Hessian, rank 10, three power updates/four full operator calls, one target call; 512/45,500 actual training records and 512/5,000 target records; seed 0 for total sampling/subspace, seed 1 for target sampling; cutoff `max(1e-6, 1e-5*lambda_max)`.

All three runs kept all ten Ritz directions. None converged or stopped early. Maximum relative residuals were 0.169854, 0.209588 and 0.193532, versus tolerance 0.001. Their sum-rule errors were respectively 1.68e-7, 3.07e-7 and 2.04e-7. The sum rule checks algebra inside the computed subspace, not approximation of the population Hessian or ranking quality.

## Other behavioral changes bundled with the speed work

These must not be described as harmless runtime refactors:

1. Full projected target matrix `F=U.T H_T U` now retained; previously only its diagonal was used, imposing commutativity. Whitening and row norms now match PDF equations 55–58. This is a theory correction that can change masks.
2. Curvature population changed from all 50,000 training-dataset records (including 4,500 held-out validation records) to the 45,500 examples actually used for training. This fixes a population mismatch while the 512 cap introduces a separate sampling approximation.
3. Selection changed from nearest cumulative value then strict `score > threshold` to the smallest prefix reaching mass, deterministic ties, no selection for zero mass or zero request. This matches PDF section 12. For unique scores it usually adds one/two previously excluded coordinates per parameter tensor; ties can have larger effects. At 100%, correctly selects nearly every positive-score coordinate. The resulting broad destructive reset is an intervention issue, not evidence that the score's sum rule is wrong.
4. Recovery template now receives `.train()`/`.eval()` calls; previously its unregistered dictionary-held model retained its old mode. ResNet BatchNorm now uses batch statistics during recovery and updates running buffers. This is a real optimization-behavior change bundled with the scatter implementation; must be tested on ResNet separately from a linear-layer equivalence test. PDF does not specify BatchNorm recovery behavior.
5. Parameter-name mapping now retains exact original names rather than replacing every underscore with a period. This avoids corruption for modules containing underscores (including ResNet BatchNorm state names); parameters themselves in standard ResNet do not contain such underscores, while buffers already followed a separate mapping. Dtype/device of selected parameters now inherit base parameters instead of constructing default CPU float32 vectors. Current CIFAR was already float32.

## Important non-changes and preexisting approximations

- Rank 10, top-magnitude-H subspace selection, only one recovery epoch, 40 original/gold epochs, SGD 0.01/0.9, ResNet architecture, resize-to-64 preprocessing, batch sizes 128, per-parameter-tensor grouping, zero initialization of selected weights and the ten-point 0–100% sweep all predate this runtime change. Most are present even before the September structural refactor (`29a7ebe:test_configs_2.py`).
- No AMP, FP16, BF16, quantization, training early stopping, reduced full-training epochs, reduced training-set sizes for original/gold/recovery, minibatch size reduction, or new optimizer was introduced in the audited interval.
- Direction chunking to one HMP direction was introduced one commit earlier (`939ab74` vs `d9dbd74`) to avoid CUDA's 32-bit indexing limit. It preserves rank/operator, is a memory control rather than truncation, and is inherited by the new HVP path.
- The September 9 batch/device forwarding fix predates the speed work; it repaired the spectral wrapper's propagation to the shared runner. Current active config sets all four batch sizes to 128 before training; no new speed-related batching change altered that.
- Score reuse across a percentage sweep **already existed**: it was computed once in the test object's constructor. LiRA bank reuse across repetitions **also already existed** at `939ab74` (constructed before the repetition loop). The prior runtime report overstated their novelty; the actual savings were conditional bank creation, fewer shadows and fewer audited cases.
- The PDF explicitly warns that large Hessian eigenvalues need not correspond to large target-information ratios, and demands rank/threshold sensitivity checks. Rank 10 is therefore an inherited unvalidated approximation, not a validated consequence of the formula.

## Prior performance claims: what they do and do not establish

`RUNTIME_VALIDATION.md:80` compared old BackPACK block products (24.037 s) with full-autograd products (0.491 s) on **two 64×64 ResNet images, rank 2, CPU, two threads**, one warmup/two measurements: approximately 49× on that small CPU benchmark. These products represent different curvature operators. This is neither a same-score equivalence result nor a CIFAR GPU end-to-end speedup and must not be multiplied blindly by the ~80× reduction in record visits.

`RUNTIME_VALIDATION.md:97` compared sparse reconstruction (2.113 ms) and indexed scatter (0.757 ms), approximately 2.8×, on a 1024×1024 linear layer, batch 32, CPU, one thread. Equal linear-layer outputs/gradients do not establish equivalence of BatchNorm training-mode behavior in ResNet. An extra small 32×32 test improved 0.253→0.145 ms.

The prior real-MNIST check (`RUNTIME_VALIDATION.md:104`) trained on 2,048 records for three epochs, evaluated on 512 test records, used rank 4/two updates and a 10% score-mass mask. The 512-record score took 8.02 s and recovery 1.05 s; initial training took only 5.16 s. It preserved utility in that bounded task but was **slower than its short training baseline**, did not establish forgetting or LiRA, and did not validate the CIFAR configuration.

The newly supplied CIFAR logs finally provide actual GPU deletion timings: score construction 8.86 / 4.98 / 4.98 s (approximately; prefer the persisted stage timing precision), with 40-epoch gold training around eight minutes. These should be used for the cost forecast, charging score once per deletion plus selection and the proposed recovery epochs. The full experiment includes eight shadow trainings, three original trainings, three gold trainings, random-control recovery and repeated evaluations, so its wall-clock total must not be compared with a single retraining operation. Increasing samples/iterations should be forecast from GPU stage measurements as a first-order scaling estimate and verified, not presented as a proven speedup or accuracy restoration.
